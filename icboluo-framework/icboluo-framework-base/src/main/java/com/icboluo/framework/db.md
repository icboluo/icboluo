## 索引失效

当作为状态值的时候，如果该值的出现的比率较高，则索引失效

    首先进入该值的节点，然后进入下一个节点，这是用索引
    进入下一个节点（虽然节点数多，但是只走树的一个分支，很可能比较快），这是用全局扫描

索引要求离散度较高，才有区分度，没有使用索引是因为mysql优化认为不用索引效率更高

group by 和order by的时候，很容易造成效率低下，可以对count语句进行优化

- 联合索引的效率和普通索引的效率一致
- 联合索引（a，b，c）相当于创建了a、ab、abc索引，最左匹配，对于b相当于没有创建索引，所以，创建联合索引的时候 需要仔细点

uuid类型的主键，使用的时候用索引；自增类型的主键，使用的时候不用使用索引

mysql全表扫描对应explain中的all，是对数据进行一行一行的扫描

避免数据类型转换，会使索引失效

## 索引

* not in 没有使用索引
* not exist 使用到了索引

必定出现的left join 中需要加上索引，不一定出现的不需要加，where条件同理

普通查询会用到覆盖索引，只要查询的字段都有索引就不会回表

子查询的结果集无法使用索引

hash算法无法范围查找，一般不用做mysql索引

缺点：

索引太多会增加执行计划生成时间，也会增加修改时间

b+ 树 ：多路查找树

b+树更适合范围查找，找到一个数据的时候，可以把data链表中的数据同时带出来

b树只能通过中序遍历

因为b+树可以一次查询多个数据，所以，b+树io次数远小于b树

b+树的数据都在data中，查询效率比较稳定

b+树非叶子节点没有data，可以把索引加载到内存中提高效率

mysql 的索引分为一级主键索引和二级索引，二级索引的叶子节点上存储的是主键

聚集索引：索引结构和数据一起存放的索引：主键索引；二级索引属于非聚集索引

覆盖索引就是where什么查出来什么。2个一样的，并且有索引

## 数据结构

B+树 数据存储在叶子节点；页分裂是针对于数据结构的紧凑而言的

B+树比B树的优点

B+树节点上没有存储数据，所以B+树每次可以读取更多的数据；相当于IO次数减少了

B+树遍历更加方便，B树需要遍历整棵树，B+树仅需要遍历叶子节点（B+数所有的叶子结点都在同一层，会用链表将他们串起来

B+树数据获取效率相当，基本不怎么变化，因为数据都存储在叶子节点上

## 易错点

mysql在处理字符串与整数数据对比的时候，会依次将字符串与整数数据对比，直到字符串不为整数的字母为止

## 什么是覆盖索引？

    覆盖索引的作用是避免回表再二次查找，一个索引的叶子节点里，已经包含了查询所需要的所有列，查询不再回表（回到主键索引的完整数据行）去取其他字段
    联合索引是最左匹配原则，匹配上最左边的就可以了，剩下的字段是可用可不用的，比如说，可以同时有中文字段和英文字段; 但是sql查询可以仅取中文字段

    从数据结构层面来说：mysql的默认存储引擎是InnoDB；InnoDB的索引类型有2种：
    聚簇索引/主键索引：数据行与主键索引在一起（B+树），非叶子节点存的是主键值，用于定位；
    叶子节点存完整的数据行（所有的用户列和隐藏列，例如事务id、如果没有主键，innodb偷偷建的自增聚簇索引建）已数据页（默认16KB）为单位挂载磁盘上，数据是存在这的
    我们可以看到的一行一行的数据，其实就是聚簇索引的叶子结点的数据页

    辅助索引/二级索引/普通索引：叶子节点存索引列+主键值，所以主键值越小越好（例如自增id）；
    查询的时候先查辅助索引拿到主键，再回到 聚簇索引取整行（回表）
    回表=多一次磁盘/内存查找，数据量大（百万）时是性能杀手，覆盖索引就是不用回表，因为覆盖索引（普通索引）的叶子节点上，已经存在了需要查的字段的内容，就不需要再回表查整行数据了

## 什么是随机Io

    顺序IO（相当于数组），数据在磁盘上是挨着的，读第一块数据就能预判第二块数据在哪个位置，机械硬盘磁头基本不用动
    随机IO（相当于列表/链表），数据散落在磁盘各处，每次都要把磁头挪到一个新位置，慢；
    SDD没有磁头，随机访问也明显慢于顺序访问（一次随机IO大约0.1-10ms，取决于磁盘，回表是逐行进行，命中几千行就要几千次随机），且开销更大
    开销更大：SDD是读写是以页为单位，读一行也得把这一页数据取出来，写一行也得把这一页数据清理掉；还有GC抖动、并行性用不上；随机访问慢一个数量级，而且延迟不稳定

## 为什么覆盖索引能解决随机IO的问题？

    如果是聚簇索引，根据普通索引查出来的多个id，对应的数据行在聚簇索引里面不一定挨在一起，可能分布在不同页，每次取一行，都要跳到磁盘上一个新的位置，这就是一次随机IO；
    根据普通索引查出来的行越多，数据越分散，随机IO次数越多，越慢
    覆盖索引时，查询要的列就在B+树的叶子节点里，而且这些叶子节点在磁盘上是按索引顺序紧密排列的
    命中的索引记录在树里是连续的一段（数据页），一次定位就能顺着扫过去，不需要跳到别处取数据（没有随机IO）；甚至可以只读索引页（比读数据页更小更集中），性能好得多
    磁盘IO（尤其是随机IO)是数据库最大的性能瓶颈，比CPU计算慢几个数量级；所以避免回表=使用覆盖索引，是mysql优化里性价比最高的一招
## 回表=随机io?

    回表不一定会导致随机io（随机io针对的是命中多条数据的场景），例如遇到内存缓存/多行命中的主键落在同一数据页/主键连续，数据页按序相邻
    磁盘最小的读写单位是页，如果命中的数据在同一页，就只需要一次IO就能读到多行数据
    主键连续、数据页按序相邻是说，需要几次IO，但是因为页相邻，机械硬盘的磁头几乎不动（这就是顺序读），次数没省，但每次IO成本接近顺序IO，很快
    因为命中的主键连续，导致数据行落在相同/邻的数据页，这个要用自增主键，uuid不仅会让b+数插入分裂，也会造成回表的时候不会顺序访问
    命中的行分散在不同数据页且不在缓存，这才是典型的随机IO；命中大量分散的冷数据页时，才会退化成大量随机IO

## 避免回表=用覆盖索引吗？

    覆盖索引是最主要，最常用的手段，避免回表的路子还有：
    索引下推：把where条件里能下推的列在索引层过滤，减少回表行数
    主键查询：聚簇索引，不用回表
    减少返回列/字段拆分
    冗余/反范式
    联合索引

## 怎么建联合索引呢？

    where过滤条件，高区分度列在左/快速缩小范围
    group by 分组，索引只需要与group by 列顺序一致，即可以利用索引有序性消除临时表/排序，与区分度无关
    mysql where和group by 搭配的时候一次也只能用一个索引
